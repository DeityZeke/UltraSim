# S0.5 Acceptance Report — Admission and Optional Accounting

Status: Accepted after independent adversarial review and repair

Date: 2026-08-13

Profile: `integration-s0.5-admission-accounting`

Authoritative plan: [`S0 Integration Design.md`](S0%20Integration%20Design.md)

## Result

The same concrete `ServerRuntime` now drives two game-owned entry policies:

- accountless admission creates and binds a live playable ECS entity without
  constructing Accounting, an Account, or a CharacterRecord;
- account-backed admission resolves a trusted local identity, opens a real
  CharacterSelect UI through the S0.4 semantic path, and resolves the selected
  character's durable identity in the active generation.

Admission and Accounting remain game/domain assemblies. Runtime contains no
account, character, login, UI, or admission policy.

## Accepted architecture

`Game/Accounting` owns stable account and character IDs, minimal account
status, ownership/slot/display facts, prefab provenance, and
`PersistentEntityKey`. It does not duplicate transform, health, needs, or
inventory truth from ECS. Character identity, per-account slot, and durable
entity linkage are unambiguous.

`Game/Admission` owns the two explicit policies and the typed game-owned
`CharacterSelectUi` definition. `IAdmissionEntityBinder` is the narrow game
policy seam for creating or validating playable entities. Its false create
result must be transactional; unexpected callback failure crosses a terminal
Runtime boundary because active-world mutation could already be partial.

`ServerGameFacet` replaces Luna's assembly-friend shortcut. It provides one
synchronous, owner-thread-bound callback over the active generation. It does
not expose a world/generation property, hosts do not expose it, and Server
Runtime has no dependency on Game assemblies. Trusted callbacks must not
retain the world as a second authority route.

S0.6 tightened this same rule for Accounting: account-backed Admission now
obtains typed Accounting state from the active generation callback instead of
retaining a separate store reference. Accountless Admission still requires no
Accounting state at all.

The original S0.5 `LocalAdmissionUiPort` adapted `LocalSemanticLink` without
Network, JSON, packets, or sockets. The S0 acceptance-hardening pass supersedes
that feature-specific event adapter with the neutral `IUiSemanticPort` and
`LocalUiSemanticPort`; each open view now binds one authoritative action
endpoint with explicit lifetime.

## Admission semantics

- Expected invalid participant, missing Accounting, unknown identity,
  disabled account, absent UI, stale/missing durable identity, ownership, and
  playable-policy failures return explicit `AdmissionRejection` values.
- Cold CharacterSelect open publishes a session only after receiving a valid,
  uniquely owned view ID. Expected open failure leaves no session or route.
- Hot reopen is defined only for a participant already waiting on a selector.
  It retires the prior route before opening and leaves no stale view mapping
  when close/open fails. It cannot demote an entered binding back to waiting.
- Typed Play intent is checked against the account's actual CharacterRecord,
  not trusted merely because a row ID was supplied by a client.
- Durable identity resolves against the current active ECS generation. A
  foreign persistent world, absent persistent ID, rejected playable entity,
  or entity/character already controlled by another participant rejects.
- Entry authority commits before selector disposal. A renderer close failure
  cannot make the old view route authoritative again.
- Admission sessions and Accounting share Runtime/UI's owner-thread model.

## Independent-review corrections

Luna's five happy-path tests passed, but the slice was not accepted as
submitted. Review found and corrected these issues:

- Runtime granted the entire Admission assembly unrestricted internal access
  through `InternalsVisibleTo`, coupling generic Runtime to one game assembly.
  This became the generic callback-scoped `ServerGameFacet`.
- The acceptance fixture first admitted an accountless participant and then
  bound a second participant to that already-controlled entity. The repaired
  fixture uses distinct playable entities and Admission rejects duplicate
  entity/character control.
- Cold UI open and hot reopen could leave partially published sessions or stale
  view routes after invalid IDs, duplicate IDs, or exceptions.
- Hot reopen accepted an already-entered session, changed it back to waiting,
  and retained the old Entity/CharacterId, creating ambiguous control state.
- A selector row ID from another account was not covered adversarially.
- The alleged stale durable-reference test covered only a foreign world, not a
  missing entity ID in the correct world.
- Accounting allowed duplicate character slots and duplicate
  `PersistentEntityKey` linkage, and accepted invalid `AccountStatus` values.
- Admission and Accounting lacked an explicit owner-thread boundary.
- The original `LocalAdmissionUiPort` never detached from `LocalSemanticLink`;
  the corrected neutral adapter owns and releases that forwarding lifetime.
- Admission disposal stopped on the first UI close failure instead of attempting
  all retained views.
- A game callback exception had no explicit policy despite possibly leaving
  partial active ECS mutation; it now terminally faults Runtime.

## Verification

The focused Admission suite passes 15 tests in Debug and Release covering:

- genuinely accountless entry with no Accounting instance;
- both policies against the same Runtime with distinct playable bindings;
- cold CharacterSelect, hot reopen, typed row action, dynamic disabled Play,
  and successful durable binding;
- foreign-world and exact missing-entity rejection;
- unowned row injection and duplicate playable control rejection;
- explicit configuration rejection without session publication;
- transactional cold-open failure, duplicate view ownership, and failed hot
  reopen cleanup;
- deterministic character ordering and minimal domain facts;
- duplicate character/slot/durable-link and invalid-status rejection;
- Admission and Accounting owner-thread enforcement;
- local UI-port detachment and exhaustive multi-view disposal.

The Runtime suite adds two permanent facet tests: availability/lifetime/thread
semantics and terminal callback-failure behavior. Its existing host-surface
test proves no mutable world root, while the Hosting suite separately proves
Internal and Headless hosts expose neither Runtime nor its game facet.

Accepted commands:

```text
dotnet run --project \
  _Tests/UltraSim.Game.Admission.Tests/UltraSim.Game.Admission.Tests.csproj \
  -c Release

dotnet run --project \
  _Tests/UltraSim.Server.Runtime.Tests/UltraSim.Server.Runtime.Tests.csproj \
  -c Release
```

No S0.5 API is installed in an ECS hot loop, and this slice makes no new
allocation or throughput claim. Existing Runtime, ECS, UI, client, and Godot
performance guards remain the applicable regression evidence.

## Deferred to S0.6+

Accounting is still an in-memory game-generation/domain collection, not yet a
save-set participant. Transactional ECS + Accounting preparation, cross-
participant reference resolution, coherent generation publication, and
canonical Accounting recapture belong to S0.6.

Passwords, portal tokens, rate limits, generalized admission hooks,
customization UI, remote transport, and disconnect/session-rebinding policy
remain deferred.
