# S0.7 Acceptance Report — Game-Owned ECS Inventory Vertical

Status: Accepted after adversarial correction and cross-layer regression validation

Date: 2026-08-13

Authoritative plan: [`S0 Integration Design.md`](S0%20Integration%20Design.md)

## Executive result

S0.7 now proves a small real game subsystem across Content, ECS, Runtime,
Accounting/Admission, UI, and transactional Persistence without creating a
generic Inventory kernel.

The canonical fixture is Alice with a Backpack containing Bread x5 and an Iron
Sword. Character, container, item, containment, equipment, quantity, and
durable relationships are authoritative ECS state. The four entity kinds are
created through compiled prefab content rather than ad hoc archetype creation.

`InventoryIndex` is generation-owned derived state. It provides O(1) item
location, equipment-slot lookup, and packed container-child lists. Removing or
moving an interior row repairs the one swapped donor row rather than shifting a
list. UI projections sort by persistent entity ID, so presentation order remains
canonical even though physical index order is intentionally packed.

## Corrected contracts

The adversarial review identified several weaknesses in the original slice.
The accepted implementation corrects them as follows:

- Domain creation and destruction update ECS and `InventoryIndex` together.
  Normal inventory code no longer needs a rebuild to see a newly created item,
  and destroyed/equipped items cannot remain as stale child rows.
- `MaximumItems` bounds both live indexed items and the aggregate child-slot
  capacity reserved by all container lists. `MaximumContainers` and
  `MaximumItemsPerContainer` remain separate limits. The accounting snapshot
  reports all three limits and current reserved child slots; it explicitly does
  not claim CLR object-header, hash load-factor, or allocator-alignment bytes.
- Expected capacity, stale-handle, source, kind, quantity, and slot failures are
  proven before ECS mutation. Unexpected failure after proof is an invariant
  failure, not a retryable rejection with a compensating gameplay mutation.
- Index rebuild constructs and validates replacement maps first. Invalid ECS
  truth leaves the previously published index untouched.
- The inventory Gump contains one item list with a row-selection action and
  separate Split/Equip buttons. It no longer renders duplicate item lists to
  obtain two row actions.
- UI sessions retain persistent container/item IDs. Actions resolve those IDs
  against the current generation, making post-restore use generation-safe.
  Close failure preserves controller ownership; disposal is idempotent, tries
  every view, and surfaces the first close failure after cleanup.
- S0.7 publishes one aggregate game root containing Accounting and Inventory
  state. Admission and Accounting persistence consume capability interfaces, so
  the Runtime remains opaque and game-agnostic.
- Save-set persistence contains the real `world` and `accounting` participants.
  Inventory has no duplicate artifact. Staged ECS entity references are remapped,
  the derived index is rebuilt before publication, and ECS + Accounting + Index
  become visible through one generation swap.

Raw ECS writes that alter inventory topology are outside the game-domain
contract. `InventoryGenerationState` is the normal authority for inventory
create/move/split/equip/destroy operations; `Rebuild` is the cold restore/repair
boundary for deriving the index from authoritative ECS truth.

## Public implementation surface

- `InventorySchema` exposes stable component registrations and persistence
  codecs for composition into a game schema.
- `InventoryContent` defines the Character, Backpack, Bread, and Iron Sword
  prefabs and returns world-bound compiled handles.
- `InventoryGenerationState` owns prepared lookups, the prefab handles, limits,
  game-domain mutations, projections, and the derived index.
- `InventoryGameGenerationState` is the minimal aggregate root implementing
  Accounting and Inventory capabilities.
- `InventoryUiController` projects the active generation into the existing
  compiled UI/local semantic-link/client path.
- `InventoryRuntimePersistence` coordinates ECS and Accounting participants,
  rebuilds Inventory state in staging, and publishes the aggregate root once.

No reflection, private ECS storage access, second inventory database, or
inventory-specific Runtime API is used.

## Correctness evidence

The focused suite passes 15 tests covering:

- compiled prefab provenance and immediate index maintenance;
- deterministic fixture reconstruction and indexed enumeration;
- accepted Move, Split, Equip, item destroy, and empty-container destroy;
- stale item/container, wrong source, invalid kind/quantity, full destination,
  occupied slot, non-empty container, and reservation-limit rejection;
- no ECS liveness/change-version mutation for expected preflight failures;
- packed-row donor repair and stable persistent-ID projection order;
- transactional failed index rebuild;
- one Accounting + Inventory generation root used by account-backed Admission;
- one-list Gump selection, disabled actions, stale row rejection, and delta-only
  accepted Split/Equip updates;
- ECS reference remap for character ownership plus contained and equipped item
  parent links, including rebuilt equipment-slot lookup;
- ECS + Accounting save/load, old-world invalidation, hot UI reopen, and
  Admission resolving the restored character;
- failed staged index rebuild leaving the active world/generation untouched;
- owner-thread confinement, idempotent disposal, close failure ownership, and
  attempt-all cleanup.

## Provisional performance baseline

The focused Release executable measures the S0.7 candidates in-process after
warmup. Enumeration, accepted/rejected Move, Split, and Equip use 21 samples;
rebuild uses seven samples. Mean and p95 are reported. The accepted hot mutation
and enumeration loops allocate zero managed bytes on the caller thread. Rebuild
is deliberately cold and allocation-bearing because it transactionally builds
replacement maps.

Representative accepted-run results on the development host:

| Operation | Mean | p95 | Timed managed allocation |
| --- | ---: | ---: | ---: |
| Enumerate 10 rows | 39.2 ns/container | 39.4 ns | 0 B |
| Enumerate 100 rows | 362.0 ns/container | 391.7 ns | 0 B |
| Enumerate 1,000 rows | 2.253 us/container | 2.668 us | 0 B |
| Accepted Move | 673.5 ns/op | 1.723 us | 0 B |
| Rejected Move | 50.8 ns/op | 52.4 ns | 0 B |
| Accepted Split | 1.102 us/op | 1.206 us | 0 B |
| Accepted Equip | 510.1 ns/op | 578.1 ns | 0 B |
| Rebuild, 1,000 items | 0.185 ms | 0.216 ms | 294,248 B/op |

These are provisional integration baselines, not immutable cross-generation
benchmarks. They are intended to expose regressions and pathological API shapes.
The benchmark index reserves 2,000 child slots for two 1,000-capacity containers.

## Deliberate limits

S0.7 is a fixture, not the final semantic inventory API. It intentionally omits
merge/stack policy beyond Split, multiple equipment slots, nested containers,
trade/bank/vendor policy, quantity-entry widgets, scheduler-driven inventory
jobs, and a standalone generic Inventory kernel. Process-wide memory accounting
and immutable benchmark artifacts remain work for the integrated S0.8 baseline.

The next slice should consume this surface in the complete host scenario rather
than expanding Inventory breadth speculatively.
