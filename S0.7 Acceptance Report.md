# S0.7 Acceptance Report — Composed Game Inventory Vertical

Status: Accepted after adversarial composition, identity, content, UI-delta, and index-memory correction

Date: 2026-08-13

Authoritative plan: [`S0 Integration Design.md`](S0%20Integration%20Design.md)

## Executive result

S0.7 proves a small real game subsystem across generated ECS composition,
compiled content, Runtime, Accounting/Admission, UI, and transactional
Persistence without creating a generic Inventory kernel or making Inventory the
game's integration root.

The canonical fixture remains Alice with a Backpack containing Bread x5 and an
Iron Sword. A third Apple prefab and an ownerless World Chest prove that item
behavior and container ownership are content facts rather than hard-coded
Inventory kinds.

## Accepted dependency and ownership shape

```text
Game/Inventory
    inventory components, rules, derived index, content-authoring helpers

Game/Contracts
    narrow participant/admission policy types shared without a Client dependency

Game/Composition
    one generated GameSchema
    concrete game content catalog
    GameGenerationState(Accounting + Inventory + Content)

Game/Persistence
    whole-game ECS + Accounting staging and atomic publication

Game/UI
    inventory view/session workflow over the generic UI protocol
```

Inventory depends only on ECS. It does not depend on Accounting, Admission,
Client, UI, Runtime, or Persistence and does not own sibling game state.
Composition depends on ECS, Accounting, Inventory, Runtime, and the narrow game
contracts assembly—not the Admission/UI implementation or Client.Core.

`GameGenerationState` is the concrete authoritative aggregate root. The game
persistence coordinator owns the ECS + Accounting participant set, rebuilds
Inventory's derived state in staging, and publishes the coherent candidate once.
Inventory contributes rebuild/validation; it has no separate saved artifact.

## Schema and content contracts

- Inventory components use stable generated component declarations but own no
  numeric `ComponentId` values and no closed `InventorySchema`.
- `GameSchema` is the one closed generated schema and includes unrelated game
  simulation/character components. Final dense IDs are assigned globally in
  canonical-key order.
- `InventoryItem` contains relationship, equip slot, and quantity. Prefab
  provenance supplies durable item identity and presentation.
- Optional `InventoryStackPolicy` and `InventoryEquipCapability` components
  supply behavior. There is no `InventoryItemKind` enum or item-kind switch.
- Bread, Iron Sword, and Apple are defined in concrete game content. Adding
  Apple required no edit to Inventory mutation/index code.
- `InventoryContainer` contains capacity. Optional
  `InventoryContainerOwner` independently supplies attachment/ownership, so
  backpacks and ownerless chests use the same Inventory machinery.
- Creation and rebuild validate registered content provenance and the exact
  owned/ownerless prefab shape before publication.

## Derived index contract

ECS components are authoritative. `InventoryIndex` is generation-owned,
bounded, rebuildable acceleration with O(1) item location and equipment lookup.

Contained items occupy a global dense child-node pool. Each container stores
only head/tail/count/capacity metadata. Empty containers do not allocate a
`List<Entity>`, wrapper, or their theoretical gameplay capacity. Interior
removal unlinks one node, moves the final physical node into the hole, and
repairs that donor's links/location.

The accounting snapshot reports known child-pool bytes separately and explicitly
excludes CLR dictionary buckets/entries, headers, load-factor slack, and allocator
alignment. The 100K-container gate proves:

```text
100,000 empty containers × gameplay capacity 20
theoretical gameplay slots: 2,000,000
configured/allocated child nodes: 32
contained rows: 0
known child-array bytes: 640
whole-process managed bytes after GC: ~9.86 MB at 0/10K/100K
process working set: ~59.0 MB at 10K and 100K
```

The dictionaries still consume managed metadata and are pre-sized to configured
maxima, so most of that bounded cost is already present in the zero-container
snapshot. The test does not misrepresent known child bytes as total process
memory. Managed/working-set values are same-process retained snapshots, not
isolated ownership accounting, but they directly reject the prior
per-container-list/capacity-reservation growth shape.

Rebuild constructs and validates a replacement index before swapping it into
the generation. Stale parents/owners, orphan policy components, content-policy
disagreement, excess capacity, and duplicate equipment fail without altering
the published index.

## Mutation and UI contracts

Move, Split, Equip, create, and destroy preflight expected rejection before
mutating ECS truth. An unexpected post-proof failure remains a terminal game
invariant failure under Runtime's callback policy.

UI sessions retain `PersistentEntityKey` (world + entity), not a bare
`PersistentEntityId`. Every action proves that the retained world matches the
active persistent world before resolving compact row IDs. A stale view from
World A therefore cannot target a numerically identical entity ID in World B;
the view is rejected and retired.

Successful operations publish semantic row deltas:

```text
Split -> Update(source row) + Add(created row)
Equip -> Remove(equipped row)
```

No accepted Split/Equip emits `UiListPatch.Replace`, performs a new ECS
container snapshot, or closes/reopens the view. The retained generic `UiModel`
still creates its own immutable row-array snapshot when applying patches; that
is UI-kernel backing storage, not a full inventory projection or wire refresh.

## Persistence and runtime publication

The save set contains `world` and `accounting` artifacts only. Persistent ECS
references remap container owners and contained/equipped item parents. During
load, ECS and Accounting remain staged, Inventory rebuilds from the staged ECS,
and `GameGenerationState` publishes once. Failed rebuild leaves the active
world/generation unchanged; successful publication invalidates old runtime
handles.

The composition's world-to-content association uses weak world keys, preventing
disposed generations from being retained solely by the content lookup seam.

## Correctness evidence

The corrected focused suite passes 17 tests covering:

- globally composed generated schema IDs and persistence catalog identity;
- aggregate-root rejection of cross-world Inventory/content state;
- compiled content provenance and transactional index rebuild;
- generic third-item creation/splitting without an Inventory kind edit;
- owned backpack and ownerless world-container semantics;
- content-derived container presentation (the world chest is not titled Backpack);
- wrong prefab/ownership preflight with no entity creation;
- policy-driven Move, Split, Equip, capacity, and stale/source rejection;
- dense child-pool donor-link/location repair;
- 100K mostly-empty-container storage scaling;
- Accounting + Admission + Inventory through one game generation;
- exact Split `Update + Add` and Equip `Remove` patches, with no `Replace`;
- adversarial different-world/same-entity-ID UI ABA rejection;
- contained and equipped relationship persistence/remap/reindex;
- failed staged Inventory rebuild preserving active publication;
- owner-thread confinement and idempotent UI disposal.

## Provisional performance controls

The focused Release test intentionally labels exactly what is timed:

- **resolved child scan**: scan an already-resolved `InventoryItemCollection`;
- **lookup + child scan**: call `GetItems(container)` inside the timed operation,
  then scan;
- **hot same-item/two-container ping-pong**: a deliberately cache-hot lower
  bound, not representative world traffic.

A representative run on the development host reported:

| Control | Mean | p95 | Timed managed allocation |
| --- | ---: | ---: | ---: |
| Resolved 1,000-child scan | 1.481 us | 1.109 us | 0 B |
| Lookup + 1,000-child scan | 1.494 us | 1.684 us | 0 B |
| Hot same-item/two-container ping-pong | 651 ns | 1.071 us | 0 B |

The resolved scan's mean exceeding p95 reflects one noisy upper-tail sample in
this short in-process run. These are provisional integration controls, not
immutable publication benchmarks. They correct the earlier mislabeled
“enumerate container” measurement.

## Deliberate limits

S0.7 remains a fixture, not the final broad inventory product. It omits merge,
multiple equipment slots, nested containers, trade/bank/vendor policy,
quantity-entry UI, scheduler-driven inventory jobs, and immutable standalone
benchmark artifacts. Those capabilities should be added only when a subsequent
simulation/product slice establishes their real contracts.

S0.8 should consume `Game/Composition`, `Game/Persistence`, and `Game/UI`; it
must not reintroduce a feature-owned aggregate root.
