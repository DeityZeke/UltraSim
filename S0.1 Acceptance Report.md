# S0.1 Acceptance Report — ServerRuntime and ServerGeneration

Status: Accepted after independent adversarial review

Date: 2026-08-12

Profile: `integration-s0.1-runtime-generation`

Authoritative plan: [`S0 Integration Design.md`](S0%20Integration%20Design.md)

## Objective and scope

S0.1 adds the first real authoritative runtime root without importing the V2
server facade. `ServerRuntime` is concrete and host-neutral. A trusted game
composition configures a private ECS candidate through a cold, callback-scoped
builder; Runtime owns schema capture, sealing, initialization, ticking,
publication, replacement, and disposal.

The slice does not add hosts, UI, Network, Accounting, Inventory, save-set
participant composition, commands, admin, settings, or discovery.

## Accepted contract

- `ServerRuntime` has explicit `Created -> Initialized -> Running -> Stopped`
  lifecycle plus terminal `Faulted` and idempotent `Disposed` cleanup.
- `ServerGeneration` is the internal coherent root containing the real V3
  `EcsWorld` and generation-owned `WorldClock`.
- Hosts receive lifecycle control and bounded status, not the mutable generation
  root or an arbitrary generation-replacement command.
- `IServerComposition` supplies one schema captured at runtime construction and
  configures each cold candidate. Its builder/world are callback-scoped
  capabilities, not a second active-world authority.
- Candidates are configured, sealed, initialized, and started privately before
  publication. A scheduled-system fixture proves real ECS execution, but an
  otherwise valid empty composition is not forbidden merely to satisfy the test.
- Publication is one `_currentGeneration = candidate` root transfer. The old
  generation is disposed only after that boundary. Pre-publication failure
  reclaims the candidate and leaves the active root unchanged.
- A failure after root transfer is terminal: Runtime retains the newly published
  root, faults, and never attempts an unprovable rollback.
- The host supplies monotonic elapsed durations. Step-count calculation is
  transactional; invalid/oversized elapsed input rejects before accumulator or
  simulation mutation and does not fault a healthy runtime.
- Fixed simulation steps, world time, and playback use deterministic integer
  state. The mechanism-neutral world-time default is 1x; the 24x S0 fixture is
  explicit game/test configuration rather than Runtime policy.
- Normal server playback is fixed at 1x. Variable playback requires an explicit
  offline-host option. Playback changes how quickly tick N is reached, not what
  tick N means.
- `WorldClockSnapshot` is the persistable state contract and discards transient
  host elapsed residue. Actual durable save-set ownership remains S0.6 work; S0.1
  does not pretend an in-memory snapshot is already a persistence participant.

## Findings corrected during review

The initial Luna implementation had the correct architecture, but four details
needed correction before acceptance:

1. Its single fixed-order benchmark result (`1.033`) was not reproducible with
   normal tiered compilation; repeated runs ranged broadly and included a severe
   tiering outlier. The control now uses 21 alternating A/B samples, reports mean
   and p95, and accepted evidence fixes TieredCompilation and ReadyToRun off.
2. An excessive `Tick(elapsed)` request updated the host accumulator before
   throwing and the wrapper then terminally faulted the runtime. Calculation now
   commits only after validation, while actual simulation failure remains fatal.
3. “At least one scheduled system” was a fixture requirement promoted into a
   runtime restriction. The scheduler remains required, but zero registered game
   systems is a valid cold composition and has a regression.
4. The initial public surface exposed both the mutable active generation and an
   unconditional replacement operation to hosts. Both are now internal controlled
   seams; public host observation is limited to generation/tick/time/playback
   status.

The review also changed the default world-time rate from game-specific 24x to
neutral 1x, froze the composition schema once, and made the test system state
distinct per generation instead of retaining one authoritative counter on the
long-lived composition object.

## Test evidence

The focused suite passes 13 tests covering:

- lifecycle rejection and idempotent cleanup;
- a real scheduled ECS system;
- a valid empty composition;
- the narrow host-visible surface;
- owner-thread rejection for host control, observation, and disposal;
- transactional invalid elapsed rejection;
- failed replacement isolation;
- coherent root publication and per-generation system state;
- stale old-world handles and disposal ordering;
- terminal post-publication failure;
- exact 24x world-time advancement over 216,000 fixed 60 Hz steps;
- clock snapshot restoration and 4x playback equivalence at equal ticks;
- warmed zero-allocation ticking;
- repeated alternating direct-ECS/runtime performance measurement.

Accepted measurement command:

```text
DOTNET_TieredCompilation=0 DOTNET_ReadyToRun=0 \
dotnet run --project _Tests/UltraSim.Server.Runtime.Tests/UltraSim.Server.Runtime.Tests.csproj -c Release
```

Representative reviewed row:

```text
samples=21 ticks_per_sample=2000
direct mean/p95 = 924,100 / 933,800 ns
runtime mean/p95 = 948,167 / 957,200 ns
wrapper ratio = 1.026
delta = 12.03 ns/tick
```

This is a local minimal-fixture guard, not a cross-machine claim. Repeated fixed-
JIT controls stayed within the design's approximate 2–5% investigation band.
The warmed caller hot path allocated zero managed bytes.

The unchanged ECS, generator, and save-set transaction suites also pass after
the review.

## Known boundary

Trusted composition code necessarily receives the cold `EcsWorld` to register
archetypes and systems. The API documents that capability as callback-scoped;
retaining it would violate the composition contract. Preventing malicious trusted
composition from retaining an object reference would require a broad revocable
registration facade over the generated ECS API and is not justified for S0.1.
Hosts do not receive that capability.

## Exit gate

One concrete `ServerRuntime` runs one real ECS generation, executes scheduled
simulation, and replaces the entire authority root through a controlled internal
boundary. Runtime remains engine-neutral and game-policy-free, old ECS identities
do not resolve in the replacement, and the wrapper remains allocation-free with
measured low fixed overhead. S0.2 may now add only the host wrappers and minimal
typed capabilities required by the authoritative plan.
