# S0.6 Acceptance Report — Real ECS and Accounting Persistence

Status: Accepted after adversarial review, atomic-root correction, and expanded regression validation

Date: 2026-08-13

Authoritative plan: [`S0 Integration Design.md`](S0%20Integration%20Design.md)

## Result

The real `ServerRuntime` now saves and restores both the authoritative ECS
world and game-owned Accounting through one durable save-set sequence. Accounting
captures deterministic account, trusted-identity, character, prefab, and
`PersistentEntityKey` facts. It does not duplicate ECS component state.

Load prepares both participants privately, resolves every Accounting character
link against the staged ECS participant, validates the complete candidate, and
constructs one `ServerGeneration` containing the staged ECS world and staged
Accounting state. Publication is exactly one active-generation reference
assignment. The old ECS world and old Accounting state retire together only
after that assignment. Runtime has no dependency on Accounting or other
game-domain types; its generation state is opaque.

## Implemented seams

- `Game/Persistence/AccountingSaveSetParticipant` is a bounded deterministic
  binary participant with canonical ordering and sequence validation.
- `RuntimeAccountingPersistence` is the game-owned bridge for real ECS +
  Accounting save/load composition.
- Prepared participants can expose staged persistent identities to later
  participants; Accounting resolves `PersistentEntityKey` values only against
  the staged ECS world in this composition.
- `ServerGenerationBuilder.SetGameState` installs one opaque game-owned state
  root into a private candidate. `ServerGameFacet` provides typed,
  callback-scoped use of ECS plus that paired state.
- `ServerGameFacet.TryPublishPreparedGeneration` transfers both prepared roots
  into the candidate before publication. There is no post-swap state-transfer
  callback.
- `AccountingStore` supports immutable capture, isolated staged reconstruction,
  explicit retirement, and stale-use rejection. Admission no longer retains an
  independently authoritative Accounting object; it resolves Accounting from
  the same active generation callback as ECS.
- Accounting decoding applies configured artifact/count bounds before
  proportional allocation and rejects noncanonical order, normalized-string
  drift, invalid status, truncation, trailing bytes, and sequence disagreement.

Inventory remains ECS-authoritative and is not a separate S0.6 participant.

## Verification

The focused S0.6 suite passes all eleven tests:

- deterministic Accounting artifact capture and staged entity resolution;
- configured byte/count limits and canonical-order enforcement;
- duplicate durable character-link and unresolved validation rejection;
- real Runtime save/load of ECS + Accounting with one generation publication;
- byte-exact ECS and Accounting recapture under a normalized capture context;
- missing staged character entity rejection with active generation unchanged;
- Accounting preparation-limit failure with active generation unchanged;
- real Accounting domain validation failure with active generation unchanged;
- participant/save-set sequence disagreement with active generation unchanged;
- ECS preparation-limit failure with active generation unchanged;
- candidate construction rejection with both staged roots reclaimed and the
  active generation unchanged.

The missing-reference failure test also creates a new entity after the failed
load and verifies that the live persistent-ID allocator continues at the
expected value. Successful load verifies the saved component value, restored
character record, callback-visible ECS/Accounting pairing, stale old-world and
old-Accounting disposal, and old-handle invalidation.

The Runtime suite now has sixteen tests. Its generation-owned-state regression
injects failure after private game-state construction, verifies cleanup without
active-root change, observes the candidate ECS/state pair during the one
publication hook, and verifies that old ECS/game state retire together.
